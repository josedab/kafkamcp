# KIP-1318 Compatibility & Adapter Boundary

> **Time-sensitive:** KIP-1318 (a proposed first-party Kafka MCP capability) is an
> evolving Apache Kafka Improvement Proposal. Details below reflect the proposal
> as understood at **review date 2026-07** and must be re-verified against the
> current KIP discussion before implementation. Do not treat this as a claim of
> certified compatibility.

## Intent

KafkaMCP does **not** aim to out-CRUD a first-party Kafka MCP server. If/when a
standard first-party server exists (KIP-1318), KafkaMCP should be able to:

1. **Coexist** — run alongside a first-party server, providing the
   governance/approval/masking/audit layer the first-party primitives lack.
2. **Delegate** — forward baseline primitive operations (topic/schema/group
   read, produce/consume) to a first-party server behind KafkaMCP's identity,
   policy, and approval enforcement, rather than reimplementing them.

This keeps KafkaMCP focused on its wedge (secure, vendor-neutral governance)
instead of competing on primitive parity.

## Adapter boundary

The delegation seam is a small, explicit interface. Baseline capabilities are
expressed as a provider that KafkaMCP can back either with its own Kafka clients
(today) or a first-party/KIP-1318 server (future), without changing the
enforcement path:

```
Agent ──▶ KafkaMCP (identity, policy, approval, masking, audit)
                      │
                      ▼
             BaselineProvider  ◀── swappable
              ├── native (franz-go clients)  [current]
              └── kip1318 (delegate)          [future]
```

Design constraints for the future adapter:

- **Enforcement stays in KafkaMCP.** Identity resolution, default-deny
  authorization, approval-grant consumption, masking, and audit logging all
  happen in KafkaMCP *before* any delegation. The adapter never bypasses
  `withToolAuth` / `enforceApproval`.
- **Read/write split is preserved.** Delegated read operations map to
  `core-read`; delegated mutations remain in `ops-write` and require approval.
- **No capability inflation.** The adapter exposes only baseline primitives; it
  does not re-expose experimental/simulated surfaces.
- **Vendor neutrality.** The same adapter contract must be satisfiable by Apache
  Kafka, Redpanda, MSK, and Confluent baselines.

## Compatibility checklist (to complete when KIP-1318 stabilizes)

- [ ] Confirm the KIP-1318 tool/method names and schemas against the final KIP.
- [ ] Map baseline read primitives to `core-read` tools.
- [ ] Map baseline mutations to `ops-write` tools + approval scopes.
- [ ] Implement a `kip1318` BaselineProvider behind the adapter boundary.
- [ ] Add a conformance harness comparing native vs. delegated results on a
      local cluster.

## Non-goals

- Claiming live certification or interoperability without an executed conformance
  harness and cited evidence.
- Reimplementing first-party primitives where delegation is cleaner.
